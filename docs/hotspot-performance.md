# Hotspot visibility performance

`HotspotLayer` prepares one visibility evaluator per rendered frame and shares each marker's answer with pointer-lock reticle targeting. Marker positions and projected vectors are retained between frames; button visibility and occlusion attributes are written only when their values change. Builder reveal continues to show hidden markers without making them visitor reticle targets.

The evaluator rejects points outside all three projected clip axes before occlusion work, including panorama markers. It traverses visible camera-layer meshes once, updates transforms and retains world-space geometry boxes. Ray segments only intersect candidate meshes whose boxes overlap the segment to the marker, stopping at the first blocking mesh and preserving the existing 7 cm surface tolerance. It checks meshes directly instead of recursively raycasting every scene object for every marker.

Answers are cached until camera/projection, mesh membership/visibility/layers, transforms, geometry/index versions or material identity/version/side change. Editing a marker creates a fresh result. Removed resources are dropped from the evaluator. Skinned, instanced and morph meshes conservatively invalidate answers every rendered frame and bypass static box rejection. Ordinary transform animations refresh their boxes immediately. No additional frame timer is introduced: demand rendering already suppresses stationary frames; moving camera and animated occluders get immediate updates. A slower marker update rate is deferred until device profiling justifies a latency tradeoff. Room visibility metadata is documented in [room streaming](room-streaming.md).

## Reproducible evidence

From `web`, run `npm run benchmark:hotspots`. This uses the versioned 160-marker/four-room fixture and preserves the original visibility algorithm within the benchmark. It verifies in-view answers against that algorithm across camera turns, warms both paths, then records three 180-frame runs for stationary, panning and adjacent-room panning workloads. The optimized measurements include scene synchronization and cache checks. Both paths count actual mesh raycast calls; early full-view rejection is an intentional behavior change. Override `HOTSPOT_PERFORMANCE_OUTPUT` to choose the JSON destination.

[phase3-hotspot-cpu.json](performance-baselines/phase3-hotspot-cpu.json) records local Node CPU/work measurements. Median visibility CPU time per rendered frame decreased from 0.6443 to 0.0343 ms stationary, 0.5642 to 0.0672 ms panning, and 0.8221 to 0.1316 ms panning from the adjacent room. Actual mesh raycasts over 180 frames decreased from 691,200 to 0, 605,568 to 0, and 691,200 to 10,608 respectively. The first two poses need no mesh intersections after bounds/surface-tolerance rejection; the adjacent-room workload retains real wall intersections. These exclude React/DOM, renderer submission, GPU and total browser frame time, and are not physical-device acceptance or production budgets. Stationary **rendered** frames exercise cache reuse; normally demand rendering stops those frames entirely. Wall occlusion, moving walls, hierarchy visibility, geometry changes, layers, projection changes and conservative instance behavior are separately covered by unit tests.

[phase3-chromium-smoke.json](performance-baselines/phase3-chromium-smoke.json) contains the six-scene software-renderer instrumentation reports plus embed. The existing hotspot acceptance command covers placement/edit/save, visitor hiding, builder reveal, preview, reticle activation, panorama, public/embed and touch. Run it with `TOUR_ORIGIN=http://localhost:5173 TOUR_FRONTEND_ORIGIN=http://localhost:5174` when the source Vite frontend uses port 5174; the source proxy preserves the storage CORS origin.

The hotspot, fan-animation and six-scene instrumentation checks passed. The [chunking acceptance report](chunking-acceptance.md) records the later full walking checks, including public courtyard exits and returns.

Remaining acceptance: same-device sustained browser CPU/frame-time comparisons and CPU/GPU profiling across supported physical device classes. Synthetic visibility CPU improvements must not be reported as total walkthrough FPS gains.
