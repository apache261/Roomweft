# Chunk contracts and source partition review

Phases 1 and 2 define and persist reviewed ownership. Phases 3–4 now generate intact static chunks and deliver scoped descriptors; see [processing and delivery](chunking-processing.md). Imported-scene and layout streaming are implemented in [Phases 5–6](chunking-viewer.md). Existing `runtime-v1` output, upload validation, scenes, floor approvals and public delivery remain compatible. Original source bytes are unchanged.

The strict contracts live in `internal/chunking`, `web/src/chunkingContracts.ts`, and the generated [JSON Schema](chunking.schema.json). Shared complete examples are in `tests/testdata/chunking/contracts/`. These are contract fixtures; their example payload hashes/bytes do not describe generated chunk files. Go and TypeScript additionally validate reference graphs, coverage, ownership, openings, readiness and authoritative source/revision associations beyond JSON Schema's structural checks.

Regenerate the schema with `go run scripts/chunking-schema.go`. Unknown fields and unsupported versions are rejected. The frontend's stored-manifest parser returns no manifest for malformed, legacy or unsupported contracts, retaining the complete-original path. No new contract is placed inside a `runtime-v1` manifest. `AssetResponse.streaming` separately advertises current chunk job state and its scoped manifest endpoint.

## Coordinate and identity rules

All inventory bounds, node matrices, room volumes, opening corners and chunk bounds are **source-space**. The source root uses path `0`; each `/index` is an actual runtime-loader child index, independent of node names. Source node/primitive indices refer to the immutable uploaded GLB. Multi-primitive meshes may produce several runtime child paths. Author-facing material and floor paths remain source paths.

A chunk's `local_to_source` affine matrix restores its local coordinates to source space. The viewer model/placement transform then applies **once**. Prepared bounds are a computed preview, never persisted as source bounds. Model scale, rotation, up-axis or layout placement changes recompute those previews; they do not rewrite partition coordinates or duplicate the wrapper. Output verification must still compare actual decoded transforms against the original; a finite affine matrix alone cannot prove equivalence.

`streaming-v1` identifies the parent UUID, source SHA-256, `chunks-v1` processor version and positive partition revision. A stable chunk ID and immutable descriptor hashes identify resources. Signed URL expiration or renewal never changes identity. Whole-file processing remains `runtime-v1`; no database derivative job is repurposed for chunk processing.

`source_node_paths` lists the source hierarchy. `source_surfaces` declares source path, primitive, triangle count and source bounds. Each `surface_map` retains source and local path/primitive plus triangle start/count ranges. Exact, non-overlapping range coverage is required for every source primitive and every declared chunk-local primitive. For example, local triangle 3 in a range starting at source triangle 20 resolves to source triangle 23 while retaining the same author path. `SourceIdentity`/`sourceIdentity` implement this resolution. A missing mapping must fail resolution, not invent a shorter author path.

`ValidateAgainst`/`validateManifestAgainst` bind otherwise self-consistent output to authoritative source inventory, parent identity, saved author metadata and the expected revision. A worker must call this before publishing and must independently verify output hashes, bytes, transforms, materials and actual loader inventory in Phase 3. Basic manifest validation alone does not prove generated bytes match the original.

## Payloads, dependencies and readiness

Each chunk declares source bounds, affine transform, primitive/triangle inventory, mappings, dependency IDs and Low/Balanced/HQ descriptors. Durable descriptors contain a private `key`, SHA-256, actual bytes, texture RGBA8 estimate and maximum texture dimension. Delivery DTOs replace `key` with a renewable `url` while retaining hashes and all chunk metadata. Private descriptors and signed delivery descriptors have separate validators/types; URL-only descriptors cannot be parsed as durable manifests. Delivery uses on-demand scoped signing, documented in [processing and delivery](chunking-processing.md); the manifest response identifies `delivery: scoped-descriptors`.

Dependencies declare texture, animation or shared-contributor payloads and prerequisite IDs. Cycles, unknown references, duplicate IDs and conflicting durable payload identities fail validation. Animation dependencies explicitly retain source node paths, clip indices and skin indices. This first contract conservatively permits one complete authored hierarchy group only with complete/global ownership; every global chunk must require it. Splitting animated groups into independently verified dependency sets needs a later supported contract/processor policy.

Regions own chunks consistent with reviewed source owners. Global contributors appear once, not in each room's visual geometry. `display_requires` includes the region's chunks and global visual contributors. `movement_requires` includes those display prerequisites plus exact `navigation` and `occlusion`. Resource prerequisites expand transitively through the dependency graph. Download/decode completion does not imply those prerequisites have prepared and committed; the future viewer must separately enforce readiness and area entry.

Navigation describes verified exact geometry and `authored-only-floors`, retaining canonical source floor paths. An empty retained-floor list is permitted for inspection-only/unapproved sources and grants no walking permission. Occlusion separately describes verified authored occluders with material, visibility and sidedness semantics. A geometry-only collision proxy cannot be declared equivalent to that representation. `fallback: complete-original` remains mandatory.

The contracts cap inventory/chunk/dependency records at 10,000, rooms/regions at 512, openings at 2,048 and encoded contracts at 4 MiB. These are admission guards, not production performance budgets. API review writes use the same 4 MiB limit. Later processing must also enforce actual output count/byte budgets and delivery size limits.

## Author review and persistence

In the builder, choose **Partition** and **Inspect original source**. Imported scenes inspect their parent asset. Layouts can select an imported parent; its partition applies to all placements of that parent. Existing template rooms and `room_id` placement ownership remain authoritative for generated layout streaming. They are not copied into a parent asset's source coordinates, since different placements may use different template rooms/transforms.

Inventory is derived on the backend from original stored bytes, with an independent SHA-256 comparison. It uses the same runtime-loader hierarchy conventions as material/floor paths and reports source bounds, glTF indices, triangle counts, geometry bytes, embedded image references and conservative dependency groups. Names help inspection but never authorize ownership, floors or portals. The inspector paginates source nodes, room groups and openings and shows per-group/global reference-byte estimates. Estimates repeat shared geometry/image references and omit export overhead; actual independent payload sizes are only available after generation.

The author assigns every renderable source contribution exactly once to a named room or the global group. Room bounds must contain their owned source bounds. A room-owned contribution intersecting another reviewed room must remain global; flat authored surfaces are treated conservatively at their plane. Crossing objects, shared walls, stairs, exterior views and uncertain contributors remain global. Changing membership recomputes room bounds, then authors can review the physical volume. Source nodes belonging to a conservative dependency group cannot move into a room. Sources containing skins, clips, morphs, instancing or unsupported contributors conservatively keep the complete source rather than claiming verified separability.

Visibility policy starts conservative. A reviewed opening has distinct source/from and destination rooms (or a null exterior view), a doorway/window kind, four ordered source-space corners and an explicit review flag. The quad must be finite, planar, convex, have nonzero area and intersect the associated reviewed room volumes. Editing its geometry or endpoints clears its review flag. These checks validate metadata structure; the author still must check the actual physical opening. It grants no walking access and never modifies explicit navigation exits or floor approvals. Unknown opening metadata remains conservative.

Migration `014_asset_partitions.sql` adds a parent-owned row containing immutable-source hash, inventory, document and revision. Existing assets require no backfill; the absence of a row selects the complete original. Initial source inspection creates revision 0 with global ownership. Saving a review increments the revision using a source-hash/revision compare-and-swap. Concurrent/stale writes return 409; **Reload saved partition review** fetches the current metadata without repeating source inspection. A same-source inventory refresh preserves authored ownership and revision. A changed source hash invalidates ownership, resets to complete/global metadata and increments the revision. Asset deletion cascades to the metadata row. Chunk jobs snapshot and compare these revisions; a reviewed-room save atomically queues the current `chunks-v1` revision.

Inventory inspection is explicit and bounded to one request per API process, 256 MiB source, two minutes and a 1 GiB Node heap. Contention returns 429. Unsupported, oversized or failed inspection leaves the original and existing review unchanged. `ASSET_PROCESSOR_SCRIPT` must point to the processor installation containing `inventory.mjs`; Docker packages both scripts. The private API uses existing parent-asset lookup rules. No public author-inventory or partition-write route is exposed.

| Route | Behavior |
| --- | --- |
| `GET /api/v1/assets/{id}/partition` | Read current review, or an explicit complete-source fallback |
| `POST /api/v1/assets/{id}/partition/inventory` | Inspect original bytes and initialize/refresh inventory conservatively |
| `PUT /api/v1/assets/{id}/partition` | Save `{revision, source_sha256, document}` after authoritative validation and compare-and-swap |

Partition writes do not touch scenes, material assignments, floors, hotspots, animations or model transforms. Static bake identity continues to use the existing whole-file source identity and geometry/material/lighting inputs. Partition revisions and future chunk hashes are deliberately excluded, so publishing partition/chunk metadata alone neither certifies nor invalidates a bake. The earlier behavior in which initial `runtime-v1` source-hash availability can change a bake key is retained for compatibility; it is separate from publishing chunk products. Actual geometry/material/UV changes still require bake review and later output verification.

## Checks and rollout boundary

```sh
npm --prefix web test
npm --prefix web run build
go test ./...
# With the current source Vite server on 5175:
TOUR_ORIGIN=http://localhost:5175 npm --prefix web run test:partition
# With a disposable database URL (test creates an isolated schema):
TEST_DATABASE_URL=... go test ./internal/httpapi -run TestPartitionPersistenceInventoryAndCAS -v
```

The browser regression covers inventory, ownership assignment, persistence, invalid crossing bounds, stale-save feedback, unreviewed openings, mobile sizing and complete fallback for skins/clips. The database/API integration verifies migration, original inventory/hash, revision conflicts, refresh preservation, invalid owners, missing fields, source conflicts, original delivery, private/public scope and oversized admission. Shared Go/TS contract checks cover coverage loss/duplication, identity ranges, dependency cycles, coordinates, exact index semantics, delivered descriptors and authoritative inventory/revision binding.

Chunk output generation and scoped signing are implemented in Phases 3–4. Partial imported-scene loading and conservative visibility are implemented in Phases 5–6. Shared dependency optimization, full eviction/storage retirement and physical-device performance acceptance remain later phases. Author review alone cannot claim download/residency savings.
